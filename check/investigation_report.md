The five requested baselines can share a modern training environment, but **changing dependency versions and model paths alone will not make these checkouts correct or runnable**. The largest blockers are SKD's patched generation engine and disabled student gradients, old KD/GKD data encoding and sampling logic, and DistiLLM-2's assumptions about an older Transformers Trainer API.

This investigation covers DistiLLM-2, ABKD's language-model branch, Speculative KD (SKD), Generalized KD (GKD), and ordinary token-level KD. It does not treat ABKD's image-classification environments as dependencies of the LLM experiment. No training-code migration is implemented in this delivery; the exact proposed configuration and subsequent changes are specified in accompanying documents.

The audit machine currently has **Python 3.12.7 and torch 2.6.0+cpu**, with Transformers 4.56.1 and Accelerate 1.10.1. CUDA is unavailable, and PEFT, TRL, and DeepSpeed are absent. Those are the observed local versions, separate from both historical versions and the proposed GPU environment.

**Proposed common version target.** Use Python **3.11.13**, PyTorch **2.6.0**, Transformers **4.51.3**, and the exact companion pins in [unified_configuration.md](unified_configuration.md). Python 3.11 satisfies the newer code's language requirements while avoiding selecting the nearly finished Python 3.10 maintenance line for a new migration. This is a fixed compatibility anchor; newer patch releases can be adopted once, with a new lock and the same verification for all baselines. [Python 3.11 release information](https://www.python.org/downloads/release/python-31113/), [Python 3.10 lifecycle information](https://www.python.org/downloads/release/python-31018/).

Qwen's official model card states that Transformers versions below 4.51.0 do not recognize `qwen3`. The recommended 4.51.3 pin clears that boundary. PyTorch supplies 2.6.0 CUDA 12.4 wheels; vLLM 0.8.5 independently requires torch 2.6.0 and Transformers >=4.51.1, making it a plausible separately installed generation backend. This reasoning supports a migration target, not a claim that old source code will run unchanged. [Qwen model card](https://huggingface.co/Qwen/Qwen3-8B), [PyTorch installation archive](https://pytorch.org/get-started/previous-versions/), [vLLM release metadata](https://pypi.org/pypi/vllm/0.8.5/json).

The Llama repositories' public API returned model revisions, but direct config/tokenizer downloads returned HTTP 401. No bypass was attempted. Therefore **exact Llama token-map compatibility is unverified**, including any changes in named special tokens between releases. The report's 128,256 dimension is supported by Meta's registry, not by a downloaded HF checkpoint. Before experiments, use authorized checkpoint access to compare token maps, merges, normalizers, special IDs, and actual model output-head shapes.

The requested unsuffixed Qwen3 checkpoints are post-trained models with thinking controls. They are not the separate `-Base` checkpoints. The unsuffixed Llama checkpoints are base models. Comparing methods within each pair is still meaningful when all five share the same initialization and prompts, but family-level results should identify this difference. For comparable instruction-tuned starting points, explicitly select corresponding Llama Instruct variants or perform a common SFT stage; that changes the checkpoint specification and must be recorded. For the proposed initial Qwen experiment, use `enable_thinking=False` consistently in training, online rollouts, offline generation, and evaluation; this is an experiment-design choice, not a claim about the model's default.

**What each baseline means in the available code.** Loss names in one trainer are not complete implementations of methods that also require a particular sampling process.

| Requested baseline | Code evidence | Baseline identity to preserve |
|---|---|---|
| KD | `distillm/finetune.py:171` and `distillm/losses.py:4`; `--type kd`, `--kd-ratio 1.0` in KD scripts | Teacher soft targets on fixed reference-response prefixes. The helper named forward KL computes soft-target cross-entropy; it has the same student gradient as forward KL but a different reported loss value. SeqKD is a separate hard-target method. |
| GKD | `scripts/gpt2/gkd/gkd_base.sh`; `finetune.py:301`; `distillm/losses.py:32` | Script uses `mixed-jsd`, `student-gen`, mixture probability 0.5; JSD uses student weight 0.9. Sampling, divergence direction, mixture weight, and replay policy must all be specified. |
| ABKD | `abkd/distillation_llm/distillm/losses.py:5`; dispatch at `finetune.py:196` | Preserve the alpha-beta divergence and its analytic limiting cases. Qwen script's alpha=0.1, alpha+beta=0.9 means beta=0.8. Its `--type ab` does not enter the `mixed`/`adaptive` generation branches despite `--student-gen`. Its supplied data path points to pseudo responses. |
| SKD | `train/ddp_skd.py:521`; `transformers/utils.py:4033` | Student proposals interleaved with teacher intervention, using the supplied teacher top-k acceptance mechanism (default k=25) and a KD loss. Ordinary HF assisted/speculative decoding is not a drop-in equivalent. |
| DistiLLM-2 | `generate/reformat.py:21`; `src/distillm_trainer.py:1073,1145,1244` | Offline teacher/student response pairs: teacher as chosen, student as rejected; teacher-side skew forward divergence and student-side skew reverse divergence. Preserve the detached student contribution in the reverse mixture. |

These interpretations are based on inspected code. The method papers also emphasize sampling as part of the objective: [GKD](https://arxiv.org/abs/2306.13649), [SKD](https://arxiv.org/abs/2410.11325), [DistiLLM-2](https://arxiv.org/abs/2503.07067). A generic `loss_type=gkd` or `loss_type=speculative_kd` in DistiLLM-2 does not generate fresh on-policy or speculative trajectories: its normal data flow loads prebuilt pairs. Those branches alone do not satisfy the requested GKD/SKD baselines.

DistiLLM-2's actual released defaults are `base_alpha_1=base_alpha_2=0.1`, `update_alpha=False`, and `gradual_beta=False` (`src/distillm_trainer.py:506`). Thus the `distillm_v2` branch uses local beta=1 and sums the two response losses. The CLI DPO `beta` is not that local beta. Automatic alpha adaptation, gradual weighting, or iterative response refresh should not be described as active in the supplied configuration. Document any such extension as a separate variant.

The SKD sampling concern in F11 is a consistency problem established from its implementation, not a claim that the paper prescribes the observed re-sampling. A corrected port must state whether it reproduces a legacy quirk or the intended proposal/acceptance algorithm. Likewise, correcting replay, masking, and data splits can change results; preserve original source snapshots and record these fixes in experimental methods.

**Resource implications.** Standardize Linux CUDA training, with this Windows checkout used for inspection/development. Existing launchers depend on Bash, torchrun/Accelerate and distributed GPU execution. The proposed CUDA 12.4 profile assumes a compatible NVIDIA driver/GPU; exact hardware was not supplied. Newer GPU architectures may require a different torch/CUDA profile, which must then be applied to every baseline.

Using nominal parameter counts, an 8B teacher in BF16 occupies about 16 GB of weights. A fully trained 1.7B student can require roughly 27.2 GB for BF16 parameters/gradients plus FP32 master weights and Adam moments (16 bytes/parameter), before activations, logits, communication buffers and caches. These are rough accounting estimates, not measured minimum VRAM. Sharding/offload and optimizer choices alter them. DistiLLM-2 computes two responses per prompt and large full-vocabulary tensors; SKD/GKD also pay for online generation. Never interpret equal prompt batch size as equal FLOPs or equal generated-token budget.

Full-vocabulary loss computation should support token chunks with exactly preserved normalization and gradients. Do not silently replace full distributions with top-k KD to save memory. Teacher acceptance top-k in SKD is a sampling setting, not permission to truncate its training loss vocabulary.

**Readiness decision.** Qwen's pair passes metadata/tokenizer compatibility checks, but all five baselines need code work before trustworthy experiments. Llama is viable at the architecture level, subject to exact checkpoint selection and tokenizer verification. The shared stack is a reasoned, metadata-checked migration target; GPU training, dependency installation, distributed checkpointing and final numerical equivalence remain acceptance tests for the later implementation, detailed in [the modification plan](codex_modification_plan.md) and [validation record](validation_record.md).
